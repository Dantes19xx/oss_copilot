# 1. Цель проекта
Задача - не «собрать демо», а спроектировать и реализовать продукт инженерного уровня: с архитектурой, мониторингом и осознанным выбором каждого технического решения. Менторы при оценке смотрят прежде всего на ваше мышление и обоснование, а не на красоту интерфейса.


# 2. Обязательные технические требования
ВАЖНО:!!!! Все пункты ниже являются критическими. Проект, в котором отсутствует хотя бы один из обязательных модулей, к защите не допускается.

## 2.1. Архитектура и оркестрация

- [x] Оркестрация агентов через LangGraph, CrewAI или Parlant. Обязательно наличие как минимум одного многошагового workflow с условной логикой (ветвления, циклы, человеческое подтверждение). — `backend/graph/graph.py`: `StateGraph`, ветвления (`route_after_intake`, `route_after_fetch_diff`, `route_after_human_confirm`, ...), 3 ограниченных цикла (`analyze_file` ≤10 файлов, `score_repo` ≤5 кандидатов, `clarify_repo_match` ≤2 уточняющих вопроса), 4 узла с `interrupt()` (`human_confirm`, вопрос в `clarify_repo_match`, `human_select`, `show_issues`); плюс управляемые человеком циклы без лимита — возврат «назад» к списку кандидатов и уточнение поиска (`refine_search` → `search_repos` → … → `human_select`).
- [x] Минимум один собственный MCP-сервер, разработанный участником и интегрированный в проект. Сервер должен предоставлять как минимум 2-3 содержательных tool'а. — `backend/mcp_server/server.py`, 8 tool'ов (`get_pr_diff`, `get_pr_files`, `post_pr_comment`, `create_pr_review`, `merge_pull_request`, `search_github_repos`, `get_repo_health`, `get_good_first_issues`), реальный MCP-протокол через `backend/graph/mcp_client.py` (in-process `mcp.Client`).
- [x] Минимум один собственный Skill (например, для Claude или аналогичной системы), оформленный по стандартам - с SKILL.md, описанием триггеров и валидной структурой. — `.claude/skills/code-review-checklist/SKILL.md`, валидный frontmatter (`name`, `description` с явными триггерами: "review this PR", "code review this diff" и т.д.).

## 2.2. Работа с данными

- [x] RAG-пайплайн с осознанным выбором: chunking-стратегия, embedding-модель, векторная БД (Qdrant / Chroma / Pinecone / pgvector), reranker (опционально, но приветствуется). — `backend/rag/`: chunking по markdown-заголовкам с fallback на fixed-window (`chunking.py`, `tiktoken`, 500 токенов/50 overlap), `text-embedding-3-small`, Qdrant (одна коллекция `repo_docs`, фильтр по `repo`). Reranker не делали — он помечен в ТЗ как опциональный.
- [x] Обработка документов или веб-сайтов: парсинг PDF / DOCX / HTML, либо скрапинг сайтов с обработкой динамического контента. — `backend/rag/document_ingest.py`: PDF (`pypdf`) и DOCX (`python-docx`) в ту же коллекцию Qdrant, что и обычный RAG. HTML-скрапинг не делали — в ТЗ варианты соединены "либо", закрывать оба не требуется.
- [x] Мультимодальность: проект обязан использовать как минимум одну мультимодальную возможность - анализ изображений, OCR, обработка аудио (speech-to-text), анализ видео или генерация изображений. Использование должно быть осмысленным, а не «прикручено для галочки». — `backend/graph/vision.py`: скриншоты/gif из описания PR анализируются vision-моделью (gpt-4o-mini), встроено в граф как условный узел (`analyze_screenshots`), находки идут отдельным разделом в финальный комментарий — влияет на реальный результат ревью, не декоративно.

## 2.3. Мониторинг и оценка

- [x] Логирование и трейсинг всех LLM-вызовов через LangSmith (или аналог - Langfuse, Weights & Biases). На защите показать дашборд с реальными трейсами. — включено через `.env` (`LANGSMITH_TRACING`, `LANGSMITH_API_KEY`, `LANGSMITH_PROJECT`), автоматически для всех `ChatOpenAI`-вызовов; `backend/rag/embeddings.py` — `@traceable` вручную (сырой `openai` SDK — не `Runnable`, иначе слепая зона). Дашборд — `smith.langchain.com`, проект `oss_copilot`, показать на защите вживую.
- [x] Evals: golden dataset не менее 30 примеров, автоматизированный прогон оценок, как минимум 2 метрики (например, accuracy + LLM-as-judge / faithfulness / relevance). — `backend/evals/golden_dataset.py`: ровно 30 примеров (6 bug, 6 security, 5 missing_tests, 5 breaking_change, 8 clean). `run_evals.py` — метрики: accuracy/precision/recall/F1 (детекция) + LLM-as-judge (0-5). Прогон автоматизирован и в CI (`.github/workflows/ci.yml`, job `evals`, на каждый PR).
- [x] A/B тестирование: как минимум один эксперимент со сравнением двух конфигураций (разные модели, промпты, температуры, RAG-стратегии) с метриками и выводами. — `backend/evals/run_ab.py`: gpt-4o-mini vs gpt-4o на golden dataset, результаты и вывод в EVALS.md.

## 2.4. Гиперпараметры и оптимизация

- [x] Документированный выбор LLM с обоснованием: почему GPT / Claude / Gemini / локальная модель. Баланс стоимости, латентности и качества должен быть описан явно. — обоснование в README.md/EVALS.md (gpt-4o-mini как основная модель — баланс стоимости/латентности/качества; A/B-эксперимент выше подтверждает выбор данными).
- [x] Подбор температуры, top_p, max_tokens - с экспериментальным обоснованием. — `backend/evals/run_temperature.py`: температура 0.0/0.2/0.7 на golden dataset (0.0 выбрана — та же точность, что 0.2, но строго лучше воспроизводимость; см. EVALS.md, включая честно описанный temperature-confound). `max_tokens=500` обоснован реальными `usage_metadata` с 60 живых вызовов. `top_p` сознательно оставлен дефолтным — задокументировано, почему (не тюнят temperature и top_p одновременно, по рекомендации OpenAI).


# 3. Рекомендуемые требования (влияют на оценку)

Эти пункты не обязательны для допуска к защите, но напрямую повышают итоговую оценку и качество проекта. Чем больше реализовано - тем сильнее проект.

- Аутентификация пользователей и базовая роль-модель.
- Голосовой интерфейс (audio-to-audio модели).
- Собственный eval-фреймворк или нестандартные метрики.
