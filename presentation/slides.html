02 / 15
Проблема

Один пользователь, две реальные боли

PR Reviewer

Разработчик хочет получить качественное автоматическое ревью своего PR до того, как звать живого ревьюера — сейчас это либо ждать часы/дни, либо выкладывать код без второй пары глаз.

Repo Matcher

Разработчик хочет начать контрибьютить в open source, но тонет в поиске "с чего начать" — звёзды на GitHub ничего не говорят о том, дружелюбен ли проект к новичкам прямо сейчас.

03 / 15
Решение

Один агент, один граф, свободный текст на входе

Пользователь просто описывает, что нужно — "review this PR <ссылка>" или "I know Python, want to contribute to a CLI tool". Классификация запроса — это и есть первое реальное ветвление графа.

  • reviewРевью файл за файлом — баги, security, тесты, breaking changes — с грaундингом в конвенциях конкретного репозитория.
  • repo_matchРанжированный список кандидатов по fit-score (CONTRIBUTING, good-first-issues, активность), не по звёздам.

human-in-the-loop  Ни один комментарий не публикуется в GitHub без явного подтверждения человека.

LangSmithтрейс каждого вызова

Ни один узел графа не ходит в GitHub или OpenAI напрямую — только через MCP tool layer или langchain_openai.ChatOpenAI, поэтому каждый LLM-вызов автоматически попадает в LangSmith.

Оба цикла ограничены (файлы ≤10, кандидаты ≤5) — не могут убежать. Обе паузы — один и тот же механизм: langgraph.types.interrupt() + Command(resume=...).

06 / 15
Собственный MCP-сервер

6 инструментов поверх GitHub API

  • get_pr_diffdiff и метаданные pull request'а
  • get_pr_filespatch по каждому файлу — для поочерёдного ревью
  • post_pr_commentwrite — вызывается только после подтверждения человеком
  • search_github_reposпоиск репозиториев-кандидатов
  • get_repo_healthCONTRIBUTING.md, good-first-issues, активность, лицензия
  • get_good_first_issuesоткрытые issue для выбранного репозитория

Граф вызывает их через настоящий MCP-протокол (mcp.Client, in-process) — не прямым импортом функций.

08 / 15
Мультимодальность

Vision-анализ скриншотов в описании PR

Скриншот или demo-гифка в описании PR — это то, что текстовый diff физически не может увидеть: несовпадение с заявленным изменением, сломанный layout, баг, видимый только на картинке.

реальный пример  facebook/docusaurus#7036 — demo-гифка в Test Plan была найдена, проанализирована vision-моделью, и вывод попал в финальный ревью-комментарий вместе с текстовыми замечаниями.

Мониторинг

LangSmith: трейс каждого LLM-вызова

  • chat + visionтрейсятся автоматически через langchain_openai.ChatOpenAI — без дополнительного кода

  • thread_idсвязывает оба ainvoke() одного HITL-сценария (до и после interrupt) в одну историю в дашборде

Accuracy = сказал ли что-то, когда должен был. Judge = совпадает ли суть комментария с реальной проблемой. Они расходятся — missing_tests: accuracy 1.00, judge всего 2.60 — модель замечает "что-то не так", но часто не то.

При t=0.7 разброс числа комментариев между повторами одного и того же файла ненулевой; при t=0.0/0.2 — нулевой. Judge-score одинаков у 0.0 и 0.2 → переключили дефолт на 0.0 — то же качество, детерминированность бесплатно.

13 / 15
Guardrails · Кэш · Fallback

Три слоя надёжности поверх базового графа

Guardrails

Diff — untrusted input. Детектор prompt-injection предупреждает человека в HITL-запросе; секреты вырезаются из комментария до публикации.

Кэш

Точный, не семантический — похожие диффы могут отличаться той самой строкой с багом. Повтор PR: 7 вызовов OpenAI → 1.

Fallback

gpt-4o-mini → gpt-4o при таймауте. Проверено реальным 0.001с таймаутом против живого API — переключение сработало.

15 / 15
Итоги

Что сделано и что дальше

Все обязательные модули ТЗ реализованы и проверены вживую: LangGraph + MCP + Skill, RAG + мультимодальность, LangSmith + evals + A/B, обоснованный выбор модели и гиперпараметров — плюс guardrails, кэш, fallback, CI/CD, Docker, публичный деплой.

Главная находка: гипотеза "модель сильнее — значит лучше" не подтвердилась данными — gpt-4o-mini выиграл у gpt-4o по recall и judge-score при 23-кратной разнице в цене.
