# TUTORIAL.md — как пользоваться OSS Copilot

Это инструкция для тех, кто хочет **пользоваться** агентом, а не читать про его
внутреннее устройство (для этого — [ARCHITECTURE.md](ARCHITECTURE.md)) или смотреть,
как шла разработка ([PROGRESS.md](PROGRESS.md)).

**Где открыть:** [oss-copilot-dmitriy-solo.vercel.app](https://oss-copilot-dmitriy-solo.vercel.app)
— рабочий деплой, ничего устанавливать не нужно. Локальный запуск и API — в конце файла.

## 1. Как устроен интерфейс

Один экран, одно текстовое поле. Вы пишете свободным текстом, что нужно, и нажимаете
**Submit**. Агент сам понимает, что вы имеете в виду — режим не выбирается вручную. Под
полем — две кнопки-примера (заполняют поле готовым запросом, можно отредактировать
перед отправкой).

**Язык ответа** — переключатель **RU/EN** в правом верхнем углу. Выбор запоминается в
браузере и действует один раз на весь запрос (сменить язык посреди диалога нельзя —
только начав новый запрос). Влияет на весь текст, который генерирует сам агент
(черновик ревью, уточняющие вопросы, статусы); данные, пришедшие напрямую из GitHub
(имена репозиториев, описания, файлы, issue) остаются как есть, не переводятся.

**Кнопка "?"** рядом с переключателем языка открывает короткую онбординг-подсказку
прямо в интерфейсе — оба режима, мультимодальность, что происходит автоматически —
если не хочется читать этот файл целиком. Закрывается по клику вне окна, на **×** или
клавишей **Esc**.

Дальше возможны два исхода:

- **Пауза с вопросом** — агент подготовил черновик (ревью, список кандидатов или
  уточняющий вопрос) и ждёт вашего решения. Под черновиком — кнопки быстрых действий
  под конкретную ситуацию (см. разделы ниже), плюс поле для свободного текстового
  ответа как запасной вариант.
- **Готовый результат** — если ответа от вас не требуется (например, запрос оказался
  непонятным), сразу покажется итог и кнопка **New request** для нового запроса.

## 2. Режим 1 — ревью pull request'а

### Как попросить

Вставьте в поле ссылку на PR вместе с просьбой на естественном языке:

```
Review the pull request https://github.com/owner/repo/pull/123
```

Формулировка не обязана быть точной — агент сам классифицирует запрос и достаёт из
текста владельца репозитория, имя репозитория и номер PR. Подойдёт и:

```
please check https://github.com/owner/repo/pull/123, is it safe to merge?
```

### Что происходит внутри (пока вы ждёте)

1. Скачивается diff и список изменённых файлов (до 10 файлов на PR).
2. Если в описании PR есть скриншот или gif — он анализируется отдельно (см. раздел 4).
3. Подтягиваются конвенции репозитория (README/CONTRIBUTING, а если вы заранее загрузили
   свой style-guide — то и он, см. раздел 5).
4. Каждый файл проверяется по отдельности: баги, security-проблемы, отсутствующие тесты,
   breaking changes.
5. Всё собирается в один черновик комментария.

Обычно это занимает 10–30 секунд на PR из нескольких файлов.

### Как выглядит черновик

Под каждым файлом — сам diff (что удалено, что добавлено, обычные `+`/`-` строки) и
список замечаний под ним, каждое со ссылкой на конкретную строку:

````
src/app.py
```diff
@@ -10,6 +10,8 @@
     def __init__(self, items=None):
         self.items = items if items is not None else []
-    def add(self, item):
-        self.items.append(item)
+    def add(self, item, qty=1):
+        for _ in range(qty):
+            self.items.append(item)
```
- L12: Новый параметр `qty` не проверяется — отрицательное значение приведёт к
  некорректному поведению.
````

Номер строки — это **строка в новой версии файла**, ровно та, что видна в diff'е выше
(не в исходном файле целиком). Если замечание касается файла в целом, а не конкретной
строки (например, "не хватает тестов"), вместо номера строки будет **"General"**/
**"Общее"**.

Номер строки вычисляется не самой моделью, а отдельно — по её точной цитате нужной
строки из diff'а, сверенной с самим diff'ом программно. Если модель процитировала
что-то, чего в diff'е не нашлось, замечание помечается как общее ("General"), а не
привязывается к случайной строке.

### Подтверждение

Вы увидите черновик комментария и три кнопки: **Approve**, **Approve & merge**,
**Reject** — нажатие сразу отправляет решение, ничего вводить не нужно. Под кнопками
есть и обычное текстовое поле (на случай, если хотите ответить не кнопкой).

- **Approve** — публикует настоящий GitHub-ревью со статусом **Approved** (зелёная
  галочка у ревьюера в PR, не просто текстовый комментарий). Если это ваш собственный
  PR — GitHub не разрешает формально одобрить самого себя (это ограничение самого
  GitHub, не наше); в этом случае агент автоматически публикует обычный комментарий с
  явной пометкой **"✅ Approved via OSS Copilot"** в начале, чтобы вердикт всё равно
  был виден, просто без формального статуса ревьюера.
- **Approve & merge** — сначала то же самое, что при Approve (ревью или комментарий с
  пометкой), а затем агент пробует смержить сам PR. Если GitHub не может смержить
  сразу (конфликты, не пройдены обязательные ревью/чеки) — это не ошибка: ревью/комментарий
  всё равно останется опубликован, а в результате будет написано, почему мерж не прошёл.
- **Reject** — черновик просто отобразится как финальный результат, никуда не уйдёт,
  в GitHub ничего не публикуется вообще — ни ревью, ни комментария.
- Если отвечаете текстом, а не кнопкой: любой нераспознанный ответ (опечатка, что-то
  непонятное) **не трактуется как reject** — агент переспросит тем же вопросом, с
  пояснением, что не понял ответ.

**Ничего не публикуется и не мержится без этого шага.** Даже если агент на 100% уверен
в ревью, GitHub не увидит ни строчки, пока вы не напишете `approve` или `merge`.

### ⚠️ Если видите жёлтое предупреждение

Иногда над черновиком появляется рамка с предупреждением о найденных в diff'е паттернах,
похожих на попытку command injection в сам агент ("ignore previous instructions" и
подобное). Это не значит, что что-то сломалось — просто автор PR (возможно, случайно
или в шутку) написал что-то похожее на команду агенту. **Внимательно прочитайте черновик
перед `approve`** — агент устроен так, чтобы игнорировать такие "команды" внутри diff'а,
но пусть последнее слово остаётся за вами.

## 3. Режим 2 — подбор open-source репозитория

### Как попросить

Опишите, что вы умеете и что ищете:

```
I know Python and want to contribute to a CLI tool
```

```
опытный frontend на React, хочу найти дружелюбный к новичкам проект
```

### Что происходит внутри

0. **Перед поиском агент может задать 1-2 уточняющих вопроса** — например, про размер
   проекта, уровень активности или конкретную область интересов, если в исходном
   запросе этого сигнала не хватает. Вопрос выглядит как отдельная пауза с текстовым
   полем и кнопкой **Skip** (если не хотите уточнять — агент просто ищет с тем, что уже
   есть). Если запрос и так достаточно конкретный, этот шаг молча пропускается.
1. Запрос (и ответы на уточняющие вопросы, если были) превращается в поисковый запрос
   по GitHub (язык, темы, минимальное число звёзд).
2. Находится до 5 кандидатов.
3. Для каждого проверяется не только популярность, а именно **дружелюбность к новым
   контрибьюторам**: есть ли CONTRIBUTING.md, сколько открытых good-first-issues, не
   заброшен ли репозиторий.
4. Кандидаты ранжируются по итоговому fit-score, не по числу звёзд.

### Выбор

Появится список кандидатов с оценками — что-то вроде:

```
1. some-org/cool-cli-tool (fit score 2.5, 4 good-first-issues) — ...
2. other-org/another-tool (fit score 2.0, 1 good-first-issue) — ...
```

...и под ним — кнопки **#1**, **#2**, ... по числу кандидатов, плюс **Skip**. Нажмите
номер интересного репозитория — агент подтянет для него реальные открытые
good-first-issues с прямыми ссылками. Нажмите **Skip**, если ни один вариант не
подошёл — агент просто завершит работу без выбора. Текстовое поле под кнопками тоже
работает (можно ввести номер или `skip` вручную).

## 4. Мультимодальность: скриншоты и gif в PR

Ничего специально включать не нужно — это работает автоматически при ревью PR (режим 1).

Если в **описании** проверяемого PR есть картинка или gif (это частая практика для
UI-изменений — "до/после", демо-запись), агент:

1. Находит до 3 изображений в тексте PR (обычный markdown `![]()`, `<img>`, стандартные
   хостинги вложений GitHub).
2. Отправляет каждое в vision-модель с вопросом: что на картинке, нет ли визуальных
   багов, ошибок интерфейса, несоответствий описанию.
3. Добавляет находки отдельным разделом **"Screenshot/attachment analysis"** в финальный
   комментарий — рядом с текстовыми замечаниями по коду.

Это ловит то, что текстовый diff в принципе не может увидеть — например, скриншот,
который не соответствует тому, что PR якобы делает, или явную визуальную поломку на
demo-записи.

Если картинок в описании PR нет — этот шаг просто пропускается, ревью идёт как обычно.

## 5. Свой style-guide (PDF/DOCX)

Если в команде есть внутренний документ со стандартами кода — не обязательно, чтобы он
жил в `CONTRIBUTING.md` целевого репозитория. Его можно загрузить заранее, и все
последующие ревью этого репозитория будут учитывать его наравне с README/CONTRIBUTING.

Это делается один раз — двумя равнозначными способами:

**Из веб-интерфейса** — кнопка **"+ Upload a style guide"** под формой запроса (пока
ответ не запрошен). Откроется окно: владелец репозитория, название репозитория, файл
(PDF или DOCX, до 10 МБ) — и кнопка **Upload**. После успешной загрузки появится
сообщение вида "Indexed N chunk(s) from ... → owner/repo".

**Из терминала** — тот же результат, тот же код под капотом:

```bash
PYTHONPATH=. python -m backend.rag.document_ingest <owner> <repo> path/to/style-guide.pdf
# или .docx
```

После этого можно сразу идти в веб-интерфейс и просить ревью PR из этого репозитория —
контекст из документа уже подключён, ничего дополнительно указывать не нужно.

## 6. О чём можно не беспокоиться

Это происходит само, без вашего участия:

- **Секреты не публикуются.** Если ревью находит захардкоженный ключ/пароль, в
  комментарии будет сказано, что он есть — но сам ключ заменяется на `[REDACTED]`, даже
  если вы нажмёте `approve`.
- **Повторный запрос быстрее.** Если вы попросите ревью того же PR второй раз без
  изменений в коде — результат придёт почти мгновенно, без повторных вызовов модели.
- **Основная модель недоступна — есть запасная.** Если модель по умолчанию не отвечает
  вовремя, агент автоматически пробует другую, не сообщая об ошибке.

## 7. Примеры целиком

**Ревью, отклонённое пользователем:**

````
> Review the pull request https://github.com/pallets/flask/pull/5918
[агент работает...]

Reviewed 5 file(s). Found 13 issue(s):

src/flask/app.py
```diff
@@ -5,7 +5,6 @@
 import os
 import sys
-import weakref
 ...
```
- L362: The addition of the `_options_view` function to `self.view_functions`
  may introduce breaking changes if existing code relies on the previous
  behavior of handling OPTIONS requests...
- ...

Reply 'approve' to post this as a PR comment on GitHub, 'merge' to post it
and then merge the PR, or 'reject' to discard it.
> reject

Reviewed 5 file(s). Found 13 issue(s):
...
(Discarded by reviewer — not posted to GitHub.)
````

(Кнопки Approve / Approve & merge / Reject делают то же самое без набора текста —
транскрипт здесь показывает текстовый путь для наглядности.)

**Подбор репозитория с выбором:**

```
> I know Python, want to contribute to a CLI tool
[агент работает...]

Candidate repositories:
1. yt-dlp/yt-dlp (fit score 2.5, 1 good-first-issues) — ...
2. chubin/cheat.sh (fit score 2.5, 1 good-first-issues) — ...
...

Reply with the number of the repo to pursue, or 'skip'.
> 1

Selected yt-dlp/yt-dlp. Good first issues:
- #4348 [gotowebinar] (https://github.com/yt-dlp/yt-dlp/issues/4348)
```

## 8. Локально и через API (для разработчиков)

Если нужно запустить не веб-версию, а из терминала или своего скрипта — см. README.md,
разделы "Запуск (локально)" и "Веб-интерфейс (Next.js)". Коротко:

- **CLI** (интерактивный ввод прямо в терминале, необязательный второй аргумент —
  язык `ru`/`en`, по умолчанию `en`):
  ```bash
  PYTHONPATH=. python -m backend.graph.run_agent "Review the pull request https://github.com/owner/repo/pull/123" ru
  ```
- **HTTP API** — те же два запроса, что использует веб-интерфейс (`language`
  необязателен, по умолчанию `en`):
  ```bash
  curl -X POST http://localhost:8000/api/agent/start -H "Content-Type: application/json" \
    -d '{"message": "...", "language": "ru"}'
  curl -X POST http://localhost:8000/api/agent/resume -H "Content-Type: application/json" \
    -d '{"thread_id": "...", "answer": "approve"}'
  ```

## 9. Если что-то не получилось

- **Агент не понял запрос** ("Could not determine whether this is a PR review request or
  a repo-matching request...") — добавьте прямую ссылку на PR (`.../pull/123`) для
  режима 1, либо явно опишите навыки/интересы для режима 2.
- **В ревью не видно упоминаний конвенций проекта** — это нормально, если репозиторий
  ещё не проиндексирован (см. README.md, раздел "RAG-пайплайн") и вы не загружали свой
  style-guide. Ревью всё равно отработает, просто без этого дополнительного контекста.
- **PR очень большой** — проверяются только первые 10 изменённых файлов; это осознанное
  ограничение по стоимости и времени, не баг.
